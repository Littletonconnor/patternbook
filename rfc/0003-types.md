# RFC 0003: Types

## Summary

The type checker is the earliest check that understands what code means. It runs on every edit, it cannot be argued with, and its errors point at the exact line. RFC 0001 places types second in its priority pyramid for that reason. A type system only catches the mistakes its types can describe, though. Where a value is typed `string` and should be one of 87 lesson slugs, or where reading an array element is typed as always present, a wrong program compiles and fails at runtime.

This RFC makes the compiler stricter and the types more exact. It turns on five compiler options beyond `strict`, derives slug types from the content data so that a typo or a missing entry fails to compile, types every link against the routes that exist, requires data from outside the program to be parsed before use, and pins one compiler version. Static types detect a measurable share of real bugs [[1]](#sources), and type information halves the compilation errors in code generated by language models [[2]](#sources). Both effects depend on how exact the types are.

## Problem

A type error is the cheapest mistake to fix: it is found before the code runs, on the line that caused it. A study of public JavaScript bugs found that adding TypeScript or Flow annotations would have caught about 15% of them [[1]](#sources). Language models frequently generate code with type errors, and constraining generation with type information cut compilation errors by more than half [[2]](#sources). An agent reads compiler errors in the same loop as it edits, so every mistake moved into the type system is fixed before anyone reviews it.

The repository already has `strict` on, `tsc --noEmit` in `verify`, and the type-aware lint rules from RFC 0004, which ban `any`, type assertions, non-null assertions and `@ts-` comments [[11]](#sources). The type layer still falls short in four ways.

### `strict` leaves known gaps open

`strict` is a group of compiler options that turns on the main family of type checks together [[4]](#sources). It does not include every check that finds bugs. Two gaps matter here.

Reading an array element or a key of a record is typed as always present. `lessons[i + 1]` has type `Lesson`, even when `i` is the last index and the result is `undefined`. The option that fixes this, `noUncheckedIndexedAccess`, adds `| undefined` to every indexed read, so the missing case has to be handled [[4]](#sources). With it on, the compiler reports 12 such reads today across 8 files, among them the homepage hero, the level cards and the `/lessons` redirect. Each one is a page that crashes if the catalog changes shape. RFC 0004 already leaves out a lint rule on the grounds that this option covers it, and the option is not on.

An optional property, such as `label?: string`, also accepts an explicit `undefined`. That makes "not passed" and "passed as `undefined`" the same type, while code that spreads props, checks `"label" in props` or calls `Object.keys` treats them differently. `exactOptionalPropertyTypes` separates the two [[4]](#sources). It reports 3 places today, all in component props.

Published strict configurations enable both options, together with several others that `strict` leaves out [[8]](#sources).

### Types are wider than the data

A type checks only what it describes. Most of the content in this repository is a fixed set known at build time: 17 topics, 87 lessons and six diagram kinds, all in `src/content`. Several types that refer to them are plain `string`:

- `Diagram.lesson` is `string`, so a diagram that names a lesson slug with a typo compiles and links to a page that does not exist.
- `topicIcons` in the sidebar is a `Record<string, LucideIcon>`. A new topic without an icon compiles and renders without one.
- `Thumbnail` maps lesson slugs to diagram kinds in a `Record<string, DiagramKind>` and falls back to `"flow"` when a slug is missing, so a typo silently shows the wrong sketch.
- The lesson source registry is a `Partial<Record<string, ...>>`, so registering MDX under a slug that is not in the catalog compiles.

Where the repository already derives types from data, the mistake cannot happen: `diagramKinds` is a `Record<DiagramKind, string>`, so a new kind without a label fails to compile, and `GlossaryId` is derived from the keys of the glossary. Agents copy the nearest example [[11]](#sources), so the wide form spreads as easily as the exact one.

### Links are checked by nothing

The site has 26 `href` props across its components. A link to a route that does not exist renders, builds and returns a 404. Next.js can type every `href` against the routes in the `app` folder, so that a link to a missing page is a type error [[7]](#sources). The option is off.

### Outside data has no rule, and the compiler is not fixed

Values from `localStorage`, cookies, URL parameters and `JSON.parse` have no static type. RFC 0004 stops them from spreading as `any` [[11]](#sources), but it does not say what replaces the `any`. The storage hooks already show the answer: each value enters as `unknown` and passes through a parse function that returns `T | undefined`. That practice is not written down, so nothing makes the next boundary follow it.

`allowJs` is on, although no JavaScript file is in the type-checked paths. Its only effect is that a future `.js` file could be imported into typed code without types.

The compiler version is not fixed either. `package.json` asks for `typescript@^5`, so any 5.x release can be installed. TypeScript does not follow semantic versioning, and its minor releases list breaking changes that can report new errors in unchanged code [[10]](#sources). Type-aware lint also runs on a second compiler, the native port behind `oxlint-tsgolint` [[11]](#sources), so the same `tsconfig.json` is read by two implementations.

## Goals

1. **The compiler checks more than `strict`.** `tsconfig.json` enables the options in part 1 of the proposal, `allowJs` is off, and `npm run typecheck` exits 0.
2. **Closed sets have exact types.** Every lesson slug and topic slug in code is typed by a union derived from `src/content`. A search in `src` for module-level constants annotated `Record<string, ...>` returns nothing.
3. **Missing entries fail to compile.** A map that needs an entry for every topic, kind or level is typed `Record<Union, ...>`, so adding a member without updating the map is a type error.
4. **Links are checked.** An `href` to a route that does not exist fails `npm run typecheck`.
5. **Outside data is parsed.** Every value from storage, cookies, URL parameters or `JSON.parse` enters as `unknown` or `string` and passes through a function that returns `T | undefined`.
6. **One compiler version.** `typescript` is pinned to an exact version, and type-checking a clean checkout needs no prior build.

## Proposal

The proposal has five parts, ordered by how many mistakes each one catches. Compiler options come first because they apply to every line, including code not written yet. Exact types from data come second because they turn the most common content mistakes, a mistyped or missing slug, into compile errors. Typed routes, parsing at boundaries and a pinned compiler each close a narrower gap.

Escape hatches are not repeated here. RFC 0004 bans `any`, assertions other than `as const`, non-null assertions and `@ts-` comments, and those bans are what make the types below trustworthy [[11]](#sources).

### 1. Compiler options

These options are added to `tsconfig.json`, each for the reason given. All exist in TypeScript 5.8 and later [[4]](#sources) [[5]](#sources).

| Option | What it does | Errors today |
| --- | --- | --- |
| `noUncheckedIndexedAccess` | Adds `undefined` to every read by index or computed key, so a missing element must be handled. | 12 |
| `exactOptionalPropertyTypes` | An optional property can be absent, but cannot be set to `undefined` unless its type says so. | 3 |
| `noImplicitReturns` | Every path through a function that returns a value must return one. | 0 |
| `verbatimModuleSyntax` | Imports without `type` stay in the output and imports with `type` are removed, so what you read is what runs. | 0 |
| `erasableSyntaxOnly` | Bans syntax that needs code generation: `enum`, namespaces with runtime code, parameter properties, `import =`. | 0 |

**Why these five.** `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` close the gaps described in the Problem section, and they are the only two that report errors today. `noImplicitReturns` catches a branch that forgets to return: without it, the inferred return type quietly widens to include `undefined`. `verbatimModuleSyntax` is the compiler side of the `consistent-type-imports` lint rule. The lint rule tells the author to write `import type`, and the compiler option guarantees what is erased and what is kept.

**Why `erasableSyntaxOnly`.** The scripts in `scripts/` run directly with `node scripts/<name>.mts`, and Node 24 runs TypeScript by removing the types, not by compiling them. Node cannot run `enum`, namespaces with runtime code, parameter properties or import aliases, and recommends both this option and `verbatimModuleSyntax` for code it runs [[6]](#sources). The option makes that a compile error everywhere instead of a crash in one script. It also covers the local `no-enum` lint rule from RFC 0004. Both stay: the lint rule reports during the edit with a message that names the fix, and the compiler option holds for any tool that type-checks.

**`allowJs` off.** No JavaScript file is in the type-checked paths. The two JavaScript config files in the root are loaded by Babel and PostCSS, not imported. With `allowJs` off, importing a `.js` file into typed code is an error, so untyped code cannot enter.

**Fixing the errors.** An indexed read that can miss is handled where it happens, usually by returning early or rendering nothing when the value is `undefined`. A loop that only needs each element uses `for...of` or an array method, which `noUncheckedIndexedAccess` does not affect. An optional prop that may receive `undefined` is either passed conditionally or declared as `label?: string | undefined`, which states that both cases mean the same thing.

#### Options considered and left out

- **`noPropertyAccessFromIndexSignature`.** It requires `obj["key"]` for keys from an index signature. With `noUncheckedIndexedAccess` on, the value is already typed as possibly missing, which is the actual risk, so the bracket syntax adds nothing.
- **`noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `allowUnreachableCode: false`.** The lint rules `no-unused-vars`, `no-fallthrough` and `no-unreachable` already report these during the edit [[11]](#sources).
- **`noImplicitOverride`.** It applies to class methods, and the repository has no classes.
- **`isolatedDeclarations`.** It requires explicit types on exports so that declaration files can be built without the type checker. It is meant for published libraries, and this repository publishes none.
- **`checkJs`.** With `allowJs` off, there is no JavaScript to check.

### 2. Exact types from data

**The practice.** When the set of valid values is known at build time, the type is that set, derived from the data so the two cannot drift apart. A value outside the set does not compile, and a map that must cover the set fails when a member is added without an entry.

**How this repository does it.** The catalog keeps its shape check and gains literal types by changing its annotation to `as const satisfies`. `satisfies` checks the data against the `Topic` type without widening it, and `as const` keeps every slug as its literal string:

```ts
export const topics = [
  /* ... */
] as const satisfies readonly Topic[];

export type TopicSlug = (typeof topics)[number]["slug"];
export type LessonSlug = (typeof topics)[number]["lessons"][number]["slug"];
```

The repository already uses this form for the level filter options and the glossary. With the unions in place:

- `Diagram.lesson` is a `LessonSlug`, so a diagram cannot name a lesson that does not exist.
- `topicIcons` is a `Record<TopicSlug, LucideIcon>`, so a new topic without an icon fails to compile.
- The thumbnail map and the lesson source registry are `Partial<Record<LessonSlug, ...>>`. Not every lesson has a sketch or an MDX file yet, so entries are optional, but a key that is not a real slug is an error.
- Functions that take a slug from inside the program, such as `lessonHref`, take the union. Functions that receive a slug from outside, such as the lesson page reading its route parameter, take `string` and narrow it with a type guard, `isLessonSlug`, as part 4 describes.

**Variant props follow the same rule.** A prop that selects a design value takes a union of names from the design scale, never a raw value. `Button`, `IconButton`, `RowLink`, `ToggleGroup` and `Link` already do this with `variant` and `size`, and `Icon` limits `size` to `12 | 14 | 16 | 20`. Props that are only valid together are a discriminated union, as `Badge` does with `tone` and `level`, so an impossible combination does not compile. This is the type-level half of RFC 0004's rules that colours and type come only from tokens.

**Why it holds second place.** Compiler options catch mistakes in any code. Exact types catch mistakes specific to this codebase, and the slug is the identifier most often copied by hand between files: from the catalog into diagrams, thumbnails, icons, the registry and links.

### 3. Typed routes

Next.js generates a type for every route in the `app` folder and, with `typedRoutes: true` in `next.config.ts`, types the `href` of `next/link` against it [[7]](#sources). A link to a route that does not exist, or a dynamic route filled with the wrong shape, is then a type error. The `Link` wrapper in `src/ui` takes its props from `next/link`, so every link in the site is covered without further changes. Hrefs built from data, such as the one `lessonHref` returns, use the generated route type.

Route types are generated files. Next.js writes them during `next dev` and `next build`, and the `next typegen` command writes them without a build [[7]](#sources). The `typecheck` script runs `next typegen` before `tsc`, so a clean checkout type-checks without a build. The page props type the lesson route already uses comes from the same generated files.

### 4. Parse at boundaries

**The practice.** Data from outside the program has no static type, whatever the code around it assumes. Parsing turns it into a typed value once, at the point where it enters, and the rest of the program works with the result. Checking a value and then passing the unchecked original along, or asserting its type, leaves every later use to trust that the check happened [[9]](#sources).

**The boundaries in this repository** are `localStorage`, cookies, URL parameters, route parameters and `JSON.parse`. Each value enters as `unknown`, or as `string` where the platform guarantees it, and passes through a parse function that returns `T | undefined`:

```ts
export type Parse<T> = (stored: unknown) => T | undefined;
```

This is the existing signature in `src/hooks/useLocalStorage.ts`, and the storage and cookie hooks already take a parser of this type. The caller decides what `undefined` means, usually a fallback value or a 404. Type guards (`value is T`) are the building block, written once per type next to the type they check. RFC 0002 already places browser storage in `src/hooks`, so new boundaries have a fixed home [[11]](#sources).

**Why no schema library.** A runtime schema library such as Zod describes a type and its parser together. That pays off with many boundaries or deeply nested external data. This site has five kinds of boundary and stores only small values such as a slug list or a level, so hand-written guards are a few lines each and add no dependency. Alternatives considered gives the best case for a library.

### 5. One compiler version

`typescript` is pinned to an exact version in `package.json`, as RFC 0004 does for Oxlint and oxfmt [[11]](#sources). Upgrading the compiler then becomes a deliberate change that fixes any new errors in the same commit, instead of a failure that appears on a fresh install.

`tsc` remains the authority for type errors, because it is the compiler Next.js and the editor use. The type-aware lint rules run on the native compiler through `oxlint-tsgolint`, which reads the same `tsconfig.json`. A new compiler option is added only when both compilers support it.

### What we learned

1. Static types catch a real but bounded share of bugs, about 15% in the one controlled study of public JavaScript [1]. Industry figures are higher but self-reported [3]. The types layer is worth its cost, but it is one layer of the pyramid, not a replacement for lint and tests.
2. Type information measurably improves generated code, halving compilation errors when generation is constrained by it [2]. This RFC goes further than the source in assuming that compiler feedback after an edit, rather than during generation, has a similar if smaller effect. RFC 0001's sources on edit-loop feedback support that assumption [11].
3. `strict` is not the strictest setting. Published configurations agree on adding `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` [4] [8]. They also add options that duplicate lint rules, which this RFC leaves to lint.
4. Running TypeScript directly in Node requires erasable syntax and verbatim imports [5] [6], and this repository's scripts already run that way.
5. Types are only as exact as their source. Deriving types from data, and parsing outside data once at the boundary, keeps types and values from drifting apart [9].

## Alternatives considered

- **Keep `strict` only.** No changes and no errors to fix. Not chosen because the 12 unchecked indexed reads are crashes waiting for a catalog change, and RFC 0004 already relies on `noUncheckedIndexedAccess` being on.
- **Extend `@tsconfig/strictest`.** One line, maintained elsewhere [8]. Not chosen for the reason RFC 0004 gives for lint presets: a preset release changes the checks without a decision here, and the preset includes options this repository leaves to lint. The options are listed by name instead.
- **Branded string types for slugs.** A brand such as `string & { readonly brand: "LessonSlug" }` marks a value as checked without listing every valid value. It suits open sets such as user IDs. Not chosen because slugs are a closed set known at build time, so a literal union is exact, needs no constructor, and gives editor completion. A brand can only be created with an assertion or a parser, and assertions are banned.
- **A runtime schema library.** Zod, Valibot and similar libraries define a type and its parser in one place and give detailed error messages. That is the better choice when external data is large or nested, such as API responses. Not chosen because this site has five small boundaries and no API, so a dependency would replace a few type guards.
- **Type-check through Oxlint instead of `tsc`.** Oxlint can report compiler errors from the native compiler during lint, which would put type errors and lint errors in one fast pass. Not chosen because Next.js and the editor use `tsc`, and two type checkers reporting different results would be worse than one slower one. It becomes the better option once Next.js uses the native compiler.

## Tradeoffs and risks

- **`exactOptionalPropertyTypes` adds friction with library types.** Library props that are optional but not declared `| undefined` reject an explicit `undefined`, so passing a maybe-missing value needs a conditional. Only 3 places are affected today. If library types make it costly, it is the first option to drop.
- **`noUncheckedIndexedAccess` flags reads that are safe.** After a bounds check, `lessons[i + 1]` is still typed as possibly `undefined`, because the compiler does not track the check. The fix is a few characters, and the reads it does catch are crashes, so the cost is accepted.
- **`as const` on the catalog makes its types longer.** Editor tooltips show deep readonly literal types, and functions that take catalog arrays take `readonly` arrays. The catalog is about 900 lines, and type-checking the whole project takes under five seconds today.
- **Typed routes depend on generated files.** If `next typegen` changes or fails, `typecheck` fails with it. External links in the `external` variant of `Link` may need a plain `string` href. Turning `typedRoutes` off restores the current behaviour without other changes.
- **Two compilers read one config.** A future option supported by `tsc` but not by the native compiler would split the two. Adding options only when both support them contains this.

Revisit if Next.js moves to the native compiler, if the site starts consuming an external API, or if a compiler option here produces errors that get fixed by adding `| undefined` everywhere instead of handling the missing case.
