# RFC 0003: Types

## Summary

A type checker proves things about a program before it runs, and its errors point at the line that caused them. That makes it the earliest check that understands what code means, and the cheapest place for an agent to find its own mistakes. But TypeScript's types exist only at compile time. They are erased before the code runs, and the compiler trusts every type it is given. Type safety therefore breaks in two places: inside the program, wherever the compiler is allowed to assume instead of check, and at its edges, wherever data arrives that the compiler never saw.

The same pitfalls recur across TypeScript codebases, and each has a known fix. Checks left off by default let `null`, missing array elements and implicit `any` through; full strictness turns them on. Escape hatches such as `any`, `as` and `@ts-ignore` switch the checker off at a single line; lint rules ban them. Types wider than the values they describe, such as `string` for a fixed set of names, let typos and missing cases compile; exact types derived from the data make them errors. Data from networks, storage and environment variables is typed by assumption; parsing it at the boundary turns the assumption into a check. This RFC proposes all four, plus measurement so that type safety cannot erode. Static types detect a measurable share of real bugs [[1]](#sources), type information halves the compilation errors in code generated by language models [[2]](#sources), and teams that enforced strictness across large codebases report that whole classes of crashes disappeared [[10]](#sources).

## Problem

A type error is the cheapest bug to fix: it is found before the code runs, on the line that caused it, by a tool that cannot be talked out of it. A study of public JavaScript bugs found that adding TypeScript or Flow annotations would have caught about 15% of them [[1]](#sources). Language models frequently generate code with type errors, and constraining generation with type information cut compilation errors by more than half [[2]](#sources). An agent reads compiler errors in the same loop as it edits, so every mistake that becomes a type error is fixed before anyone reviews it.

To use that benefit well, it helps to be precise about what the compiler does and does not check.

### Types are checked at compile time and erased at runtime

TypeScript is JavaScript with type annotations. The compiler checks that the annotations are consistent with each other and with the code, then removes them. At runtime there are only JavaScript values, and nothing compares a value with the type the code gave it. Adding runtime type information is an explicit non-goal of the language [[26]](#sources).

This splits type safety into two parts:

- **Compile-time safety** is the guarantee that, if every type in the program is true, the program uses its values correctly. It is what the compiler proves.
- **Runtime safety** is the guarantee that the types are actually true for the values that flow through the program when it runs. The compiler cannot prove this for values it never saw, such as a network response, and does not check it for values the code tells it to trust, such as an assertion.

A program is only as safe as the weaker of the two. Perfect compile-time types over an unchecked API response still crash when the response changes, because the compiler's proof started from a false premise.

TypeScript is also unsound by design. Its goals favour productivity over a provably correct type system [[26]](#sources), and it accepts some operations it cannot prove safe [[27]](#sources). The main gaps are:

- **`any`**, which turns off checking for a value and everything it touches.
- **Assertions**, `value as Foo` and `value!`, which state a type without checking it.
- **Indexed reads**, which are typed as always present unless `noUncheckedIndexedAccess` is on.
- **Method parameters**, which are checked bivariantly even under `strict`, so a method that accepts only `Dog` can be called through a type that passes any `Animal`.
- **Mutable arrays**, which are covariant: a `Dog[]` can be passed as `Animal[]`, and the receiver can push a `Cat` into it.
- **Optional properties**, which accept an explicit `undefined` unless `exactOptionalPropertyTypes` is on.

Each gap is a place where a wrong program compiles. Most can be closed by compiler options, lint rules or a choice of type, and the rest are closed by checking values at runtime. That is what this RFC does.

TypeScript projects lose type safety in four common ways.

### The checker is not fully on

TypeScript's default settings were designed to accept existing JavaScript, so many checks are off unless a project turns them on. Before TypeScript 6.0, `strict` defaulted to `false` [[4]](#sources). Without it, a missing argument type silently becomes `any`, `null` and `undefined` are accepted everywhere, and the code that crashes most often in JavaScript, reading a property of something that is not there, compiles cleanly.

Even `strict` does not turn on every check that finds bugs. Two of the most useful, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`, sit outside it [[3]](#sources). Published strict configurations add both [[22]](#sources), but a project that stops at `strict` has neither.

### The checker can be switched off from the code

TypeScript has several ways to tell the compiler to stop checking: the `any` type, type assertions (`value as Foo`), non-null assertions (`value!`), and comments such as `@ts-ignore`. Each one makes an error disappear without making the code correct. Assertions are removed at compile time and do nothing at runtime [[3]](#sources). Style guides at large organisations call them unsafe and forbid the comment forms outright [[7]](#sources).

Agents are under pressure to make the build pass, and these are the fastest way to do it. Once one exists in a codebase, the next edit copies it. Teams that migrated large codebases found that automated fixes which add `any` hide exactly the errors strictness was meant to find [[14]](#sources), and made "don't reduce type safety" a rule for every change [[13]](#sources).

### Types are wider than the values

A type checks only what it describes. Common gaps:

- **Closed sets typed as `string`.** Slugs, status names, route names and keys of a lookup table are a fixed set known at build time. Typed as `string`, a typo compiles and a missing entry falls through to a default.
- **Server and content data typed loosely.** Data rendered on the server or loaded from content files is often typed by hand, separately from the data itself, so the two drift apart.
- **Links typed as `string`.** A link to a page that does not exist renders, builds and returns a 404.
- **Optional-property bags.** An object with five optional fields allows combinations that are never valid, such as a loading state that also carries an error and a result.
- **Duplicated types.** A type written next to the value it describes, instead of derived from it, goes stale on the next change.

### Data from outside the program is trusted

Values from a network response, `JSON.parse`, browser storage, cookies, URL parameters and environment variables have no static type. Whatever type the code gives them is a claim, not a fact. A response typed as `User` because the endpoint is supposed to return a user compiles, and fails far from its cause when the server changes. Checking a value without turning it into a new type leaves every later use to trust that the check happened [[15]](#sources).

## Goals

1. **The checker is fully on.** `strict` and the additional options in part 1 are enabled, and the type check runs on every change and blocks it on failure.
2. **The checker cannot be switched off from the code.** There is no `any`, no type assertion other than `as const`, no non-null assertion and no `@ts-` comment in source. A search for each returns nothing, and lint rules fail on new ones.
3. **Closed sets have exact types.** Every value drawn from a fixed set is typed by a union derived from the data that defines the set, and every lookup over that set fails to compile when a member is added without an entry.
4. **Links are checked.** A link to a route that does not exist fails the type check.
5. **Outside data is parsed.** Every value from outside the program enters as `unknown` and is converted to a typed value by a parser, a schema or generated code at the boundary.
6. **Type quality is measured.** The share of expressions typed `any` is reported, and it can only go down.

## Proposal

The proposal has five parts, ordered by how much each one catches. Compiler options come first because they apply to every line, including code not yet written. Closing escape hatches comes second, because every other part depends on the checker not being switched off. Exact types, typed boundaries and measurement then raise what the checker can prove.

### 1. Turn the checker fully on

#### What `strict` does

`strict` is a single switch for TypeScript's "strict mode family" of options [[3]](#sources). Turning it on enables all of them:

- `strictNullChecks`: `null` and `undefined` are their own types and are no longer accepted where another type is expected. Reading a property of something that might be missing becomes a compile error instead of a runtime crash. This is the most valuable single check in TypeScript.
- `noImplicitAny`: a value whose type cannot be inferred, usually a function parameter, is an error instead of silently becoming `any`.
- `strictFunctionTypes`: function parameters are checked contravariantly, so a callback that only handles `Dog` cannot be passed where any `Animal` may arrive.
- `strictBindCallApply`: arguments to `bind`, `call` and `apply` are checked against the function's signature.
- `strictPropertyInitialization`: every class property must be assigned in the constructor or declared as possibly `undefined`.
- `strictBuiltinIteratorReturn`: built-in iterators return `undefined`, not `any`, when they finish.
- `noImplicitThis`: `this` with an unknown type is an error.
- `useUnknownInCatchVariables`: the error in a `catch` block is `unknown`, not `any`, so it must be checked before use.
- `alwaysStrict`: every file is emitted and parsed in JavaScript strict mode.

**Why it matters.** Each option removes a place where the compiler assumes the best and lets a wrong program through. `strict` is also a moving target: new TypeScript releases may add checks under it [[3]](#sources), which is the intended behaviour, since each addition catches a new class of mistakes.

**Status.** TypeScript 6.0 made `strict` the default [[4]](#sources). A project should still set it explicitly, so that the setting is visible in the config and does not depend on the compiler version.

#### Beyond `strict`

These options are not part of `strict`, and each closes a gap that `strict` leaves open.

- **`noUncheckedIndexedAccess`.** Reading an array element or a key of a record is typed as always present, even when the element does not exist. With this option, every read through an index or an index signature includes `undefined`, so the missing case must be handled [[3]](#sources). Given `const names: string[] = []`, `names[0]` has type `string` without the option and `string | undefined` with it. Given `Record<string, number>`, `scores[name]` becomes `number | undefined`. This is the same class of crash that `strictNullChecks` catches, in the place it does not reach.
- **`exactOptionalPropertyTypes`.** An optional property, such as `theme?: "dark" | "light"`, normally also accepts an explicit `undefined`. That makes "not set" and "set to `undefined`" the same type, while code that spreads objects, checks `"theme" in settings` or calls `Object.keys` treats them differently. With this option, an optional property can be absent but cannot be set to `undefined` unless its type says so [[3]](#sources). A type that means both is written `theme?: "dark" | "light" | undefined`.
- **`noImplicitReturns`.** Every path through a function that returns a value must return one. Without it, a branch that forgets to return makes the inferred return type quietly include `undefined`.
- **`noFallthroughCasesInSwitch`.** A non-empty `case` must end with `break`, `return` or `throw`.
- **`noImplicitOverride`.** A class method that replaces a parent method must say `override`, so renaming the parent method breaks the child instead of leaving a dead method.
- **`verbatimModuleSyntax`.** Imports marked `type` are removed from the output and all others are kept, exactly as written. What a file appears to import at runtime is what it does import.
- **`erasableSyntaxOnly`.** Bans TypeScript syntax that generates JavaScript: `enum`, namespaces with runtime code, constructor parameter properties and `import =` [[5]](#sources). Runtimes that execute TypeScript by removing types, including Node.js, cannot run that syntax, and Node recommends this option together with `verbatimModuleSyntax` [[6]](#sources). It also keeps TypeScript a layer of types over JavaScript, never a separate language: a union of string literals replaces an `enum`, and a plain object replaces a namespace.
- **`allowJs` off, unless a project still contains JavaScript.** JavaScript files imported into typed code bring untyped values with them. A project that is fully TypeScript turns this off so a new `.js` file cannot enter.
- **`skipLibCheck` on.** Type errors inside third-party declaration files are not the project's to fix, and checking them slows every run. The project's own code is still checked against those declarations.

Options that duplicate a lint rule, such as `noUnusedLocals` and `noUnusedParameters`, can be left to lint, which reports them with a suggested fix during the edit.

#### Enabling strictness in an existing codebase

A new project turns everything on from the first commit. An existing project usually cannot fix every error in one change. Large codebases have done it in three ways:

- **Allowlist, then denylist.** A second config with the stricter options lists only the files that already pass, and continuous integration type-checks it on every change so the list can only grow. Files are added in dependency order, starting with files nothing else depends on, so each newly strict file only imports strict files. Once most files pass, the list flips to a denylist of files still exempt, so every new file is strict by default. VS Code moved about 1,800 files to `strictNullChecks` this way from some 4,500 errors, and Figma did the same for about 1,160 files with over 4,000 errors [[9]](#sources) [[10]](#sources).
- **One option and one project at a time.** Splitting the code into separate TypeScript projects lets each option be enabled per project, keeping each change reviewable [[14]](#sources).
- **Convert everything and track suppressions.** Some migrations convert the whole codebase at once and mark each remaining error with a tracked suppression comment that is removed over time [[12]](#sources) [[13]](#sources). This finishes fastest, but leaves the checker switched off at every suppression until it is fixed.

The allowlist is the safest of the three, because the checked area can only grow. Whichever is used, two practices recur. The fix for an error is a real fix, not an annotation that silences it: adding `any`, `!` or `| null` everywhere moves the bug instead of removing it [[10]](#sources) [[14]](#sources). And every project ends on the same settings, because mixed strictness across packages changes how shared types resolve [[11]](#sources).

### 2. Close the escape hatches

Strict options only help while nothing can switch them off. The following are banned in source, and each ban is enforced by a lint rule, since the compiler accepts all of them:

- **`any`.** Use `unknown` for a value whose type is not known, and narrow it with a check before use [[7]](#sources). Code that receives an `any` from a library treats it as `unknown` at once. Lint rules also report an `any` value flowing into typed code through an assignment, argument, call, member access or return.
- **Type assertions, except `as const`.** `value as Foo` claims a type without checking it, and is removed at runtime [[3]](#sources). Where code needs a narrower type, it narrows with a check, a type guard or a parser. `as const` is allowed, because it narrows a literal to its exact value and claims nothing.
- **Non-null assertions.** `value!` claims a value is present without checking. The code checks instead, and handles the missing case.
- **`@ts-ignore`, `@ts-expect-error` and `@ts-nocheck`.** These switch the compiler off for a line or a file [[7]](#sources).
- **Wide built-in types.** `Function`, `Object`, `{}` and the wrapper types `String`, `Number` and `Boolean` accept almost anything [[7]](#sources). Use a function signature, `Record<K, V>`, a specific object type, or the lowercase primitives.

The remaining type-aware rules that protect types belong with them: exhaustive `switch` statements over unions, no floating promises, no unnecessary conditions or assertions, and only `Error` objects thrown. Published strict rule sets treat these as the baseline for type-checked code [[8]](#sources).

Where a third-party type is wrong, the fix is a corrected declaration in one place, such as module augmentation, never an assertion at each use.

### 3. Write exact types

Strict options and closed escape hatches make the checker trustworthy. What it can catch then depends on how exact the types are. This part is the difference between code that has types and code whose types prevent mistakes, and it is where agents need the most direction, because adding annotations is easy and adding useful ones is not.

#### Derive types from values

A type written by hand next to the data it describes can drift from it. A type derived from the data cannot.

- **Data defines its own types.** A fixed list of items, such as the pages of a site, the statuses of an order or the entries in a content catalog, is written once with `as const satisfies`. `satisfies` checks the data against its intended shape without widening it, and `as const` keeps every string as its literal value. The set of valid names is then derived: `type Slug = (typeof items)[number]["slug"]`.
- **Lookups over a set use the set as the key.** A map with an entry for every member is typed `Record<Slug, Value>`, so adding a member without an entry is a compile error. A map that covers only some members is `Partial<Record<Slug, Value>>`, so a key that is not a member is still an error. `Record<string, Value>` is used only for keys that are truly open, such as user input.
- **Related types come from one source.** Use `typeof`, `keyof`, indexed access, `ReturnType`, `Parameters` and `Pick` to build types from existing ones, and infer types from schemas and generated code (part 4) instead of restating them.
- **Server-rendered and content data is typed at the source.** Data that a page renders is typed where it is defined, with the same derived unions, so a page cannot render a field or reference an item that does not exist.

#### Make invalid states unrepresentable

- **Discriminated unions instead of optional bags.** A request that can be loading, failed or done is `{ status: "loading" } | { status: "error"; error: Error } | { status: "done"; data: T }`, not one object with three optional fields. Each branch carries exactly the fields that exist in that state, and the compiler narrows on `status`.
- **Props that only make sense together** are a union of the valid combinations. Props that are mutually exclusive use `never` on the other branch.
- **Exhaustiveness.** Every `switch` or lookup over a union handles every member, enforced by a lint rule or by assigning the leftover value to `never`. Adding a member then fails everywhere it is not handled.
- **Literal unions for design and configuration values.** A prop that picks a size, a variant or a colour takes a union of names from the design scale, never a raw string or number.
- **Branded types for open sets that must not mix.** Two IDs that are both strings, such as a user ID and an order ID, are distinguished with a brand (`string & { readonly brand: "UserId" }`) created only by a parser. Closed sets use literal unions instead, which are exact and need no constructor.
- **`readonly` for data that must not change.** Arrays and objects that are shared or come from configuration are `readonly`, so a mutation is a compile error. A function that only reads an array takes `readonly T[]`, which also closes the array covariance gap: a caller's `Dog[]` can be passed in, but nothing can push a `Cat` into it.
- **Function properties instead of method syntax in types.** A member written `onSelect(item: Item): void` is a method and its parameters are checked bivariantly. Written `onSelect: (item: Item) => void`, it is a function property and is checked strictly under `strictFunctionTypes` [[3]](#sources). A lint rule enforces the property style.

#### Annotate where it helps, infer where it does not

Agents tend to annotate everything, which adds noise and can widen types. The rules:

- **Annotate at boundaries.** Exported functions, component props, module-level constants and anything another file depends on get explicit types, because those types are the contract other code is checked against.
- **Infer inside.** Local variables and private helpers rely on inference [[7]](#sources). An annotation that restates what the compiler already knows adds nothing, and an annotation such as `const status: string = "done"` throws away the literal type.
- **Generics only when they relate two positions.** A type parameter earns its place when it connects an input to an output or two inputs to each other. One that appears only once should be a concrete type [[25]](#sources).
- **No widening to silence an error.** Adding `| undefined`, `| null` or `?` to make an error go away moves the bug downstream. The fix is to handle the case, or to make it impossible.
- **Optional means "may be left out", not "may be `undefined`".** With `exactOptionalPropertyTypes`, `key?: T` lets a caller omit the key, and `key?: T | undefined` also lets it pass `undefined`. The second is safe only where the reader treats `undefined` and a missing key the same, as component props do through default values and truthiness checks. Anywhere else, such as options merged over defaults with a spread, update objects where a missing key means "leave unchanged", or code that checks `"key" in value`, an explicit `undefined` overwrites a default or changes meaning. A lint rule allows `?: T | undefined` only in props types, and callers elsewhere leave the key out when there is no value.
- **One way to write each kind of type.** A project picks `type` or `interface` for object types and one array syntax, and enforces the choice with lint, so a difference in the code is always a difference in meaning.

### 4. Type the boundaries

Every value from outside the program enters as `unknown` and is turned into a typed value at the point where it enters, once. The rest of the program works only with the typed result. This is "parse, don't validate": a check that returns a boolean discards what it learned, while a parser returns a more precise type that the compiler then enforces everywhere [[15]](#sources).

#### Network data

A project that has no external data today still decides now how it will type it, so the first API call follows the rule instead of setting a precedent. The decision has two halves: where the types come from, and how every response is checked against them.

**Where the types come from.** In order of preference:

- **Shared types from one codebase.** When the client and server are in the same TypeScript codebase, a typed RPC layer such as tRPC gives the client the server's input and output types with no generated code [[20]](#sources). Inputs are still validated on the server with a schema, because the server cannot trust its callers.
- **Types generated from the API's own schema.** When the API is described by OpenAPI or GraphQL, the types are generated from that schema, never written by hand. Tools such as openapi-typescript and GraphQL Code Generator produce the types and a typed client [[18]](#sources) [[19]](#sources). The generator runs in CI and fails the build when the committed types differ from the schema, so a change on the server becomes a type error on the client.
- **A runtime schema written in the project.** When there is no schema to generate from, the project writes one with a schema library such as Zod. The schema is the single definition: the TypeScript type is inferred from it (`type User = z.infer<typeof User>`), so the type and the check cannot drift apart [[17]](#sources).

**How every response is checked.** Types from any of these sources describe what a server promises, not what it sends. A deploy on the other side, a proxy error page or a partial outage can all return something else. So every response from a server the project does not compile together with is parsed at runtime, with these rules:

- **One client module per external service.** It is the only place that calls `fetch` for that service, and a lint rule bans `fetch` elsewhere. Every function it exports returns parsed, typed data, never a raw `Response` or `unknown`.
- **Parse the body before anything reads it.** The response body enters as `unknown` and goes straight into the schema. Nothing between the network and the parser touches it, and nothing after the parser sees the unparsed value.
- **Parse into the types the program uses.** The parser converts as well as checks: date strings become `Date`, amounts in cents become a branded `Cents`, string codes become a literal union. The rest of the program never handles the wire format.
- **Failure is a value, not an exception that escapes.** A failed parse returns a result the caller must handle, such as `{ ok: true; data: T } | { ok: false; error: ApiError }`, so the compiler forces every caller to deal with the failure. The error keeps the schema's list of issues for logging, so a changed API is diagnosed from one log line.
- **Decide what unknown fields mean.** By default a schema strips fields it does not know, which lets the server add fields without breaking the client. A schema for data the program writes back, or for security-sensitive input, rejects unknown fields instead.
- **Validate what goes out as well as what comes in.** Request bodies are built from the same schemas, so a request the server would reject fails to compile.
- **Every server entry point is a boundary.** On the server side, route handlers, form submissions and server functions callable from the client receive untrusted input, even when the caller is the project's own client code. Each one parses its input with a schema before using it.
- **Real responses are test fixtures.** Saved responses from the real API are parsed in tests, so a schema that does not match reality fails before it ships.

**Choosing a library.** Any schema library that infers static types will do. Libraries that implement Standard Schema, such as Zod, Valibot and ArkType, share one interface, so form libraries, routers and RPC layers accept any of them and the choice can change later [[16]](#sources). The library is pinned like the compiler, because its inferred types are part of the type check.

#### Other boundaries

The same rule applies to every other source:

- **Environment variables.** Parsed once at startup into a typed, `readonly` object. A missing or malformed variable fails at startup, not on the request that first reads it.
- **Browser storage, cookies and `JSON.parse`.** Read through a parse function of the form `(value: unknown) => T | undefined`. The caller decides what a missing or invalid value means, usually a fallback.
- **URL and route parameters.** Arrive as `string` and are narrowed, for example to a known slug with a type guard, before use. An unknown value becomes a 404, not a crash.
- **Form input and messages from other windows or workers.** Parsed with the same schema the server uses, where one exists.

Small boundaries with simple values, such as a stored theme name, can use hand-written type guards. Once data is nested or comes from a network, the schema library is the better choice, because a hand-written guard for a nested object is long and easy to get wrong.

#### Typed links

Links are a boundary inside the program: a string that must match a route. Frameworks that know their routes can type links against them. Next.js generates a type for every route and, with `typedRoutes: true`, checks the `href` of every `Link` against it, so a link to a missing page or a dynamic route filled with the wrong shape is a compile error [[21]](#sources). Other routers offer the same through generated or inferred route types. Helpers that build links from data return the route type, not `string`. Where route types are generated files, the type-check command generates them first, so a clean checkout type-checks without a build.

### 5. Measure and hold the line

- **One command, run on every change.** The type check is part of the command that defines a finished change, and it blocks the change on failure. Large teams also build every project against each new compiler release before upgrading, so an upgrade's new errors are found before they land [[11]](#sources).
- **Pinned compiler version.** TypeScript does not follow semantic versioning, and minor releases include breaking changes that report new errors in unchanged code [[23]](#sources). The `typescript` package is pinned to an exact version and upgraded deliberately, with any new errors fixed in the same change. Where a second tool type-checks the same config, such as a type-aware linter built on the native TypeScript 7 compiler, compiler options are added only when both support them.
- **Type coverage.** A tool such as `type-coverage` reports the share of identifiers whose type is `any`, including `any` that arrives from libraries [[24]](#sources). The check fails if coverage drops below the current level, and the level is raised as it improves.
- **Suppression count.** Where suppressions exist during a migration, their count is tracked and can only go down [[9]](#sources) [[12]](#sources).

### What we learned

1. TypeScript checks types only at compile time and is unsound by design [26] [27]. Full type safety needs both strict compile-time checking and runtime checks wherever the compiler's assumptions can be false.
2. Static types catch a real but bounded share of bugs, about 15% in the one controlled study of public JavaScript [1]. Types are one layer of defence, not a replacement for lint and tests.
3. Type information measurably improves generated code [2]. This RFC goes further than the source in assuming that compiler feedback after each edit, not only during generation, has a similar effect.
4. `strict` is necessary but not sufficient. Published configurations agree on adding `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` [3] [22], and `strict` is now the compiler default [4].
5. Teams that enabled strictness at scale converged on the same method: a checked allowlist that only grows, a switch to a denylist once most files pass, real fixes instead of `any` or `!`, and one config for every project [9] [10] [11] [14]. Migrations that converted everything at once relied on tracked suppressions instead [12] [13].
6. Style guides and rule sets agree on closing the escape hatches: prefer `unknown`, avoid assertions, ban `@ts-` comments [7] [8].
7. Data from outside a program should be parsed once at the boundary into a precise type [15]. Generated types and runtime schemas are the established ways to do that for network data [16] [17] [18] [19] [20].

## Alternatives considered

- **Stop at `strict`.** The default since TypeScript 6.0, with no extra errors to fix. Not chosen because indexed reads and optional properties stay unchecked, and both cause crashes `strict` exists to prevent.
- **Extend a published strictest config.** One line, maintained elsewhere [22]. Not chosen because a config release would change the checks without a decision in this repository, and published configs include options better left to lint. The options are named one by one instead.
- **Allow escape hatches with a written reason.** Google allows assertions with an explicit reason [7], and migrations use tracked suppressions [12]. That fits teams converting existing code. Not chosen for steady-state code, because a written reason does not stop an agent from adding the next one, and a fix is almost always possible.
- **Hand-written types for API responses.** No dependency and no build step. Not chosen as the default, because a hand-written type is a claim that drifts from the server. It remains acceptable for small values from local storage, parsed with a type guard.
- **Branded types for every closed set.** One pattern for all identifiers. Not chosen because a literal union is exact, needs no constructor and gives editor completion; brands are kept for open sets such as database IDs.

## Tradeoffs and risks

- **Stricter options add friction.** `noUncheckedIndexedAccess` flags reads the author knows are safe, such as an element just checked by index, and `exactOptionalPropertyTypes` rejects library props that pass an explicit `undefined`. The fixes are small, and the errors they prevent are crashes. If library types make `exactOptionalPropertyTypes` costly, it is the first option to drop.
- **Exact types can be heavy.** Literal types derived from large data sets make editor tooltips long and type-checking slower. Splitting large data sets by area keeps this contained.
- **Generated types depend on their generators.** A broken generator or a schema out of date fails the type check. That is the intended behaviour, but it means the generator runs in CI and is pinned like the compiler.
- **Two type checkers can disagree.** While a type-aware linter runs on the native compiler and the build runs on the JavaScript compiler, an option or a diagnostic can differ between them. Pinning both and adding options only when both support them contains this.
- **Types cannot check behaviour.** A function can have perfect types and the wrong logic. Tests cover what types cannot.

Revisit when the build moves to the native TypeScript 7 compiler, when the project starts consuming an external API, or if an option here is mostly fixed by adding `| undefined` instead of handling the missing case.
